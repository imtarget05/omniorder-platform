# ADR-0001: Technology Stack & Architecture Decisions

## Status
Accepted

## Context
Building a distributed order & inventory management system that must handle:
- Concurrent purchases without overselling
- Duplicate request prevention (idempotency)
- Reliable event delivery despite failures
- Service independence and deployability

## Decision

### 1. Java 21 + Spring Boot 3.5.16
**Why**: LTS version, virtual threads (Project Loom) for concurrency, Sealed classes for state machines, record types for DTOs. Spring Boot 3.5.x supports Jakarta EE 10, Java 21 natively.

**Correction**: Proposal mentioned "Spring Boot 4.1.x" which does not exist. Using 3.5.16 (latest stable 3.x).

### 2. Oracle XE for Production, PostgreSQL for CI Tests
**Why**: Production uses Oracle (per JD requirement for transactions/indexes/execution plans). CI uses PostgreSQL via Testcontainers (lighter, no license, faster startup). Oracle-specific execution plans verified locally against Oracle XE in Docker Compose.

### 3. Transactional Outbox (not 2PC)
**Why**: Avoids distributed transaction complexity. Order + outbox in same local transaction. Scheduled poller publishes to Kafka. If crash occurs, outbox row survives and is retried.

### 4. Atomic Conditional UPDATE for Stock (not synchronous gRPC)
**Why**: gRPC call to inventory service would create coupling and cascading failure. Stock reservation must be atomic: `UPDATE ... WHERE available_stock >= qty`. This single SQL statement guarantees no oversell under any concurrency level.

### 5. gRPC for Reference Data Only (not critical path)
**Why**: Order service calls inventory via gRPC for product info (read-only reference). Critical path (stock reservation) stays event-driven via Kafka. This satisfies the "gRPC with real business logic" requirement without compromising availability.

### 6. Idempotency Key + SHA-256 Hash
**Why**: Client retry safety. Unique DB constraint on `(user_id, idempotency_key)` prevents duplicates at database level. Hash detects payload mismatch (same key, different request body).

### 7. Spring Security + Argon2id + JWT RS256
**Why**: Stateless authentication suitable for microservices. Argon2id is OWASP-recommended for password hashing. RSA-2048 keys allow public verification without exposing private key.

### 8. Kafka Topics
- `order.requested` — Order → Inventory (stock reservation request)
- `stock.reserved` — Inventory → Order (stock confirmed)
- `stock.rejected` — Inventory → Order (insufficient stock)

### 9. Outbox Topics (Order Service internal)
- Outbox table → `order.requested` (poller publishes)

### 10. Maven Multi-module + Wrapper
**Why**: Independent deployability of services, shared BOM for dependency consistency, wrapper ensures reproducible builds without system Maven.

## Consequences
**Positive**: No oversell under any concurrency, duplicate request prevention, eventual consistency via Kafka, service independence, testable with real infrastructure.

**Negative**: Eventual consistency (order CONFIRMED after stock reserved, not immediately), operational complexity of Kafka, outbox poller latency (1s default).
